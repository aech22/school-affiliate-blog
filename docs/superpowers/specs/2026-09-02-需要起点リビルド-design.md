# コドナビ 需要起点リビルド 設計

作成日: 2026-09-02 / 対象: `aech22/school-affiliate-blog`（https://code-navi.net）

## 1. 何を解決するのか

コドナビは公開から1ヶ月で、記事8本・案件19件・広告7本を持つが、次の3つが噛み合っていない。

**① 記事に本文が1文字も無い。** `scripts/generate.py` の `to_markdown()` は YAML frontmatter だけを出力し、`ArticleLayout.astro` も `<Content />` を描画していない。結果、全記事が「導入3〜4文 → サービスカード → まとめ3〜4文」で構成されている。読者から見て広告の羅列に近く、検索エンジンから見ても薄いページになる。

**② 需要と収益接点がズレている。** 承認済み12案件の内訳は 資格5/5・語学2/2・転職4/6 に対し **プログラミング1/6**。検索需要が最大のプログラミングスクール領域は承認がほぼ無く、かつ大手スクールの自社メディアが上位を占める最激戦区で、開設1ヶ月・被リンクほぼゼロのドメインでは分が悪い。

**③ 更新が止まっている。** 最終コミットは 2026-08-06。`generate.py` は手動実行で、定期実行の仕組みが無い。

## 2. 方針

**全面作り直しはしない。** 既存アーキテクチャの中核である「事実はデータファイル、LLMは講評だけ」という分離は、今回の「情報が真実である必要がある」という要件にそのまま効く。作り直すのは**記事の型と生成パイプライン**であって、サイトの骨格ではない。

作り直さないもの: `services.json` のスキーマ、`ServiceCard.astro`、`Sidebar.astro`、広告まわり、Astro/Tailwind の構成、`deploy.yml`。

## 3. 集客の軸：教育訓練給付金

制度領域を入口に置き、そこから承認済み案件へ流す。理由は3つ。

- 大手スクールの自社メディアが手薄で、検索需要が大きい
- 事実を官公庁の一次情報で固められる（＝「裏どり」要件と構造的に噛み合う）
- 「安く学びたい」は購買意欲が最も高い層

### 3.1 検証済みの土台（2026-09-02 実測）

検証記録の正本: `Obsidian/Projects/情報検証/factcheck/2026-09-02_学び支援制度_教育訓練給付金とリスキリング補助金.md`

| 制度 | 内容 | ラベル |
|---|---|---|
| 一般教育訓練 | 経費の20%・上限10万円 | ✅ 厚労省 |
| 特定一般教育訓練 | 40%・上限20万円。資格取得＋1年内就職で50%・上限25万円 | ✅ 厚労省 |
| 専門実践教育訓練 | 50%・年間上限40万円。資格取得＋就職で70%・56万円。賃金5%上昇で80%・64万円 | ✅ 厚労省 |
| 教育訓練休暇給付金 | 令和7年10月創設 | ✅ 厚労省 |

### 3.2 リスキリング補助金は土台にしない

「リスキリングを通じたキャリアアップ支援事業」は**六次公募（令和7年9月16日正午締切）をもって公募終了、七次は未定**。加えて事業者向けページに「六次公募から補助率が変更されます」とあるが変更後の数値が画像でしか示されておらず、**現行の補助率が確定できない**。

したがってこの制度は「注意喚起として扱う対象」であって、集客の土台には置かない。他サイトが古い「最大70%」を放置している現状では、**正確に「新規公募は終了している」と書けること自体が差別化**になる。

### 3.3 是正が必要な既存記述

`content/articles/remote-work-schools.md` の「リスキリング補助金に対応しており、条件を満たせば最大70%還元で実質月6,666円から」は、算定根拠が記事にも `services.json` にも無く、制度側の現行率も未確定のまま公開中。後述の検証ゲートにより、リライト時に自動的に落ちる。

## 4. 記事の型を3種類にする

現在は「比較」1種のみ。`topics.json` の各エントリに `type` を追加する。

| type | 役割 | 本文の骨格 | 案件の出し方 |
|---|---|---|---|
| `guide` | 制度解説。集客の主力 | 制度の要件 → 対象講座の探し方 → 申請の流れ → 注意点 | 文脈で1〜2件だけ |
| `problem` | 悩み起点。訴求の主力 | 悩みの言語化 → 選択肢の整理 → 判断基準 → 次の一歩 | 判断基準に紐づけて2〜3件 |
| `compare` | 既存の比較 | 選び方の観点 → 各校の位置づけ → 目的別の結論 | ServiceCard で3〜5件 |

## 5. 事実台帳 `src/data/facts.json`（裏どりの構造的担保）

### 5.1 スキーマ

```
Fact = {
  id: string,            // 例: "kyufu-senmon-jissen-80"
  claim: string,         // 例: "専門実践教育訓練給付金は賃金5%上昇で最大80%"
  value: string,         // 例: "80%（年間上限64万円）"
  numbers: string[],     // 本文に出現してよい数値表現 ["80%", "64万円"]
  source: string,        // 一次情報のURL
  sourceType: "primary" | "secondary",
  verifiedAt: string,    // "2026-09-02"
  label: "✅" | "🟡",
  note: string           // 🟡なら何が未確認か
}
```

### 5.2 検証ゲート

`generate.py` に追加する。LLM が生成した**本文から数値表現を抽出し、台帳の `numbers` に無い数値が含まれていたらその記事を破棄する**。

> **2026-09-02 実装時の修正**: 当初は `services.json` の `priceNote` も許可の根拠に含める設計だったが、実装して実データで試したところ**是正対象の記述が素通りした**。mystar の `priceNote` が「補助金適用で実質月6,666円から」そのものだったためで、未検証のレジストリ値を検証済み台帳と同格に扱っていたのが原因。許可の根拠は `facts.json` だけに限定した。料金は `ServiceCard` がレジストリから描画するので、本文が金額を書く必要はそもそも無い。

- 対象: 円・%・万円・年・ヶ月・人・件 を伴う数値
- 除外: 見出しの連番、`services` の件数など生成側が決めた数
- 破棄時はログに「未検証の数値: X」を出し、キューは進めない（同じトピックを次回再試行）
- **同一トピックが3回連続で落ちたらキューの末尾へ送り、`queue.json` に `blocked: true` と落ちた数値を記録する。** これが無いと、台帳に無い数値をLLMが繰り返し出すトピックでキューが永久に止まり、更新が静かに死ぬ

これにより、隔日の自動生成でも**事実の出所が台帳に限定される**。人間が毎回確認しなくても、台帳に無い数字は公開されない。

### 5.3 台帳の鮮度

`verifiedAt` から90日を超えた `sourceType: primary` の項目があれば、生成時にログで警告する。制度は改定されるため、鮮度切れを黙って使わない。

## 6. 本文を持たせる

- `generate.py`: `to_markdown()` を frontmatter＋本文 に変更。LLM に本文（H2 3〜5個）を書かせる
- `src/pages/articles/[...slug].astro`: `render()` して `<Content />` を `ArticleLayout` に渡す
- `src/layouts/ArticleLayout.astro`: 本文スロットを**1つだけ**追加する。位置は intro の直下、ServiceCard 群の上。分割スロット（bodyTop / bodyBottom）は作らない——記事内の順序は本文の見出し構成で表現し、レイアウト側に持たせない
- `content.config.ts`: スキーマ変更は不要（Astro の glob loader は body を自動で持つ）

## 7. 更新：隔日 cron で1本ずつ

### 7.1 仕組み

- `.github/workflows/generate.yml` を新設。`schedule: cron: '0 1 */2 * *'`（UTC 01:00 = JST 10:00）＋ `workflow_dispatch`
  - `*/2` は「日」フィールドなので 1,3,5,…,31日に走る。**月末31日の次は翌月1日で間隔が1日になる**（31日ある月のみ）。「2〜3日に1回」の範囲に収まるため許容し、複雑なスケジューラは入れない
  - GitHub Actions の schedule は負荷により数分〜数十分遅延する。定刻性は要件でないため許容する
- `scripts/queue.json` に未生成トピックの slug を積む。1回の実行で**先頭の1本だけ**生成する
- 生成 → 検証ゲート → 通過したら `content/articles/<slug>.md` を書いて main へ commit → 既存の `deploy.yml` が push を拾って公開
- キューが空になったら「キーワード補充が必要」とログに出して正常終了する（失敗にしない）

### 7.2 人間の作業

`ANTHROPIC_API_KEY` を repo secret に登録する。これだけは代行できない。

### 7.3 注意

bot が main にコミットするため、以降ローカルから push する前に `git pull --rebase` が要る（AFFILIATE.md ハマりどころ10と同じ）。

## 8. 既存8本のリライトと日付の扱い

- 新テンプレで8本とも再生成する。URL は変えない
- `date`（公開日）は `_existing_publish_date()` が維持するので 2026-08-03 / 08-06 のまま。`updated` のみ実行日になる
- **公開日は遡らせない。** 既存8本は実際に約1ヶ月前の日付を持っており、履歴は事実として存在する。加えて新記事は隔日1本ずつ出るので、大量公開による不自然さも生じない。制度情報を扱うサイトで公開日を動かすと「いつ時点の情報か」という信頼の核を壊す

公開日が外部に出ている箇所は、可視テキストの「公開 YYYY.MM.DD」と OGメタ `article:published_time` の2つ。記事ページに Article 型の構造化データは無く、sitemap に `lastmod` も無い。

## 9. トップページの是正

理由と再着手条件を明記しておく。GA4 は測定ID が手に入った時点、Pinterest は認証コードが取れた時点、案件承認は提携が通った時点で着手する。
